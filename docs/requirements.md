# 需求文档

## 简介

本需求面向 funHarness 插件新增的「工作区待办事项」（Todo）功能。待办事项是一种轻量级的记录载体，用于随手记录后续需要处理的想法、缺陷、技术债或潜在需求。

与既有的「迭代任务（迭代任务 / Task）」不同，待办事项**不隶属于任何单个迭代任务或 worktree**，而是隶属于**整个工作区**。它存储在工作区主目录的本地文件中，**不随 git 提交**，仅作为个人/团队在本工作区内的临时记录。

用户可以在**主面板（Master Panel）**添加待办，也可以在任意 **worktree 子面板（Worktree Subview）**添加待办；无论从哪个入口添加，看到的都是同一份工作区级别的待办清单。用户可对待办进行增、改、删，并可以基于某一条待办**快速创建一个迭代任务**，实现从「想法记录」到「正式迭代」的平滑衔接。

## 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 待办事项 | Todo Item | 隶属于整个工作区的轻量记录，含标题、描述、状态等字段；不随 git 提交 |
| 工作区待办清单 | Workspace Todo List | 当前工作区内全部待办事项的集合，全局唯一 |
| 主面板 | Master Panel | 工作区根目录下的主窗口视图，可管理所有迭代任务与全局配置 |
| worktree 子面板 | Worktree Subview | 为单个迭代任务打开的窗口视图，聚焦当前任务 |
| 主目录 | Master Directory | 工作区根目录，存放全局配置、主仓库与共享脚本 |
| 迭代任务 | Iteration Task | 拥有独立分支/worktree 的正式开发任务，遵循多阶段工作流 |
| 待办存储文件 | Todo Store File | 主目录下持久化待办清单的本地文件（不纳入 git） |
| 快速创建迭代任务 | Quick Create Iteration Task | 以某条待办为来源，一键生成迭代任务并预填名称/描述 |

## 需求清单

### 需求-1：在主面板添加待办事项

**用户故事：** 作为工作区使用者，我希望在主面板添加待办事项，以便于随手记录需要后续处理的事项而不打断当前工作。

#### 验收标准
1. GIVEN 用户处于主面板 WHEN 用户触发「添加待办」并填写标题（必填）与描述（可选）后提交 THEN 系统在工作区待办清单中新增一条待办，并在主面板待办列表中立即可见。
2. GIVEN 用户在「添加待办」表单中未填写标题 WHEN 用户尝试提交 THEN 系统拒绝创建并给出「标题不能为空」的提示，且不新增任何待办。
3. GIVEN 一条待办被成功添加 WHEN 系统持久化该待办 THEN 该待办被写入主目录的待办存储文件，并被赋予工作区内唯一且稳定的待办 ID。

### 需求-2：在 worktree 子面板添加待办事项

**用户故事：** 作为正在某个 worktree 中工作的开发者，我希望在当前 worktree 子面板直接添加待办事项，以便于就地记录发现的问题而无需切回主面板。

#### 验收标准
1. GIVEN 用户处于任意 worktree 子面板 WHEN 用户触发「添加待办」并提交合法内容 THEN 系统将该待办写入**工作区级**待办清单（而非隶属于当前迭代任务）。
2. GIVEN 用户在 worktree 子面板添加了一条待办 WHEN 用户随后打开主面板或另一个 worktree 子面板 THEN 该待办在所有面板的待办列表中均一致可见。
3. GIVEN worktree 子面板对根级配置存在写入限制 WHEN 用户在 worktree 子面板添加待办 THEN 添加操作被允许（因为待办属于工作区共享数据），且不触发任何根级配置或迭代任务数据的变更。

### 需求-3：工作区级持久化且不随 git 提交

**用户故事：** 作为工作区使用者，我希望待办数据仅保存在本地主目录且不进入版本控制，以便于个人记录不污染仓库历史、不影响团队提交。

#### 验收标准
1. GIVEN 存在一条或多条待办 WHEN 系统持久化待办清单 THEN 数据被写入主目录下的待办存储文件，且该文件路径处于工作区根级而非任何迭代任务的 worktree 内。
2. GIVEN 待办存储文件已生成 WHEN 用户在工作区执行 git 状态检查 THEN 待办存储文件被 git 忽略（不出现在待提交变更中）。
3. GIVEN 用户关闭并重新打开工作区 WHEN 主面板加载完成 THEN 之前保存的待办清单被完整读取并按原有 ID、内容与状态还原展示。

### 需求-4：修改待办事项

**用户故事：** 作为工作区使用者，我希望修改已存在的待办的标题、描述或状态，以便于在事项进展或理解变化时保持记录准确。

#### 验收标准
1. GIVEN 待办清单中存在一条待办 WHEN 用户编辑其标题或描述并提交 THEN 系统在保持其待办 ID 不变的前提下更新内容，并在所有面板中反映最新内容。
2. GIVEN 一条待办支持状态标记 WHEN 用户切换该待办状态（如未完成 ↔ 已完成） THEN 系统持久化新的状态且列表展示随之更新。
3. GIVEN 用户将标题清空后提交修改 WHEN 系统校验输入 THEN 系统拒绝该次修改并保留原有内容，同时给出「标题不能为空」的提示。

### 需求-5：移除待办事项

**用户故事：** 作为工作区使用者，我希望移除不再需要的待办，以便于保持待办清单简洁聚焦。

#### 验收标准
1. GIVEN 待办清单中存在一条待办 WHEN 用户对其执行移除操作 THEN 系统从工作区待办清单中删除该待办，并将变更持久化到待办存储文件。
2. GIVEN 一条待办已被移除 WHEN 用户在任意面板查看待办列表 THEN 被移除的待办不再出现。
3. GIVEN 用户移除某条待办 WHEN 移除完成 THEN 其它待办的 ID、内容与顺序不受影响。

### 需求-6：基于待办快速创建迭代任务

**用户故事：** 作为工作区使用者，我希望基于一条待办快速创建迭代任务，以便于将一个已成熟的想法直接推进为正式迭代而无需重复录入信息。

#### 验收标准
1. GIVEN 待办清单中存在一条待办 WHEN 用户对其触发「创建迭代任务」 THEN 系统进入迭代任务创建流程，并以该待办的标题预填任务名称、以其描述预填任务描述。
2. GIVEN 用户确认基于待办创建迭代任务 WHEN 迭代任务成功创建 THEN 新迭代任务出现在主面板任务列表中，且其数据与既有迭代任务遵循相同的模型与存储方式。
3. GIVEN 用户基于某条待办创建了迭代任务 WHEN 创建完成 THEN 原待办的存续行为遵循单一明确策略（保留该待办或将其标记为已转化为任务），且该策略在所有入口保持一致。

### 需求-7：待办清单查看与一致性

**用户故事：** 作为工作区使用者，我希望在主面板与 worktree 子面板都能查看同一份待办清单，以便于在任意上下文中获得一致的待办视图。

#### 验收标准
1. GIVEN 工作区存在若干待办 WHEN 用户打开主面板或任意 worktree 子面板 THEN 各面板呈现的待办清单来源于同一份工作区待办数据，内容与状态一致。
2. GIVEN 用户在某一面板对待办执行增/改/删 WHEN 用户切换到另一面板查看 THEN 另一面板在其下一次加载或刷新时呈现更新后的待办清单。
3. GIVEN 工作区当前没有任何待办 WHEN 用户打开待办列表视图 THEN 系统展示明确的空状态提示而非报错。

## 需求追踪矩阵（如有已有设计/代码）

| 需求 ID | 关联既有能力/文件（参考） | 说明 |
|---------|--------------------------|------|
| Req-1 | 主面板 webview（webviewTemplates.ts）、消息控制器（harnessMessageController.ts） | 复用现有主面板视图与消息通道新增「添加待办」入口 |
| Req-2 | worktree 子面板视图、消息控制器 worktree 限制策略 | 待办属工作区共享数据，需在 worktree 限制策略中显式放行 |
| Req-3 | 主目录 `.harness/` 非 git 存储惯例、fileOps.ts、gitService.ts | 参照 `.harness/` 下配置文件的非 git 存储与忽略惯例 |
| Req-4 | 待办存储服务（新增，参照 taskStoreService.ts 模式） | 复用持久化服务模式实现更新 |
| Req-5 | 待办存储服务（新增） | 复用持久化服务模式实现删除 |
| Req-6 | 迭代任务创建流程（harnessActionsService.ts、models.ts Task 模型） | 复用既有 `create` 任务创建路径，以待办内容预填 |
| Req-7 | 主面板与 worktree 子面板渲染（webviewTemplates.ts） | 两类面板共享同一工作区待办数据源 |
