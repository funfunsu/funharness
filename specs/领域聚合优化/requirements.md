# 需求文档

## 简介

本需求面向 Fun Harness 的“领域聚合优化”能力重构。当前流程要求先在子面板生成领域能力增量，再回到主面板执行领域裁决和领域基线聚合，导致操作链过长、上下文割裂、冲突暴露过晚。新的目标是不再受现有双面板流程约束，将“本次迭代领域增量维护、领域基线预览、冲突裁决、最终提交”收敛到子面板单一入口内完成，同时继续满足领域沉淀、可追溯、幂等和冲突可控的治理要求。

本次需求只定义“做什么”，不约束迁移方案。

## 术语表

| 术语 | 说明 |
| --- | --- |
| 子面板 | 当前迭代工作区内的单一维护入口，负责领域增量编辑、预览、冲突处理与提交 |
| 主面板 | 现有承担领域裁决和领域基线聚合的入口；本次重构后不得再作为必经维护路径 |
| 领域变更集 | 当前迭代对领域能力、契约、不变量的结构化改动集合 |
| 领域基线 | `docs/domains/` 下按 canonical domain 长期维护的领域沉淀文档 |
| 基线投影 | 将当前迭代领域变更集叠加到当前领域基线后的即时预览结果 |
| 基线版本 | 用户开始编辑时参考的领域基线版本标识，用于检测并发修改与提交漂移 |
| 命名冲突 | 同一语义领域出现多个名称，或原始领域名无法唯一映射到 canonical domain |
| 能力主键冲突 | 同一 `Req-*` 能力在并发改动中出现相互矛盾的标题、状态或归属 |
| 原子提交 | 迭代增量产物与领域基线产物要么一起成功写入，要么一起失败回滚 |

## 需求清单

### 需求-1：子面板成为领域维护唯一入口

**用户故事：** 作为迭代执行者，我希望只在子面板内完成领域增量维护、基线预览、冲突处理和提交，以便于不再在子面板与主面板之间来回切换。

#### 验收标准

1. GIVEN 用户位于当前迭代子面板，WHEN 打开领域维护功能，THEN 系统必须在子面板内同时提供领域增量编辑、基线预览、冲突处理和提交入口。
2. GIVEN 领域聚合优化能力启用后，WHEN 用户查看原主面板相关入口，THEN 原有领域裁决、领域基线聚合及其相关治理功能必须从主面板移除，不得继续显示或可触发。
3. GIVEN 用户完成一次领域维护，WHEN 全流程结束，THEN 用户不得被要求切换到主面板或其他面板才能完成领域沉淀。
4. GIVEN 子面板初始化失败或缺少必要上下文，WHEN 无法进入维护流程，THEN 系统必须在子面板内显式返回失败原因，不得伪造完成状态。

### 需求-2：子面板实时生成领域基线投影

**用户故事：** 作为迭代执行者，我希望在编辑当前迭代领域变更时立即看到它对领域基线的影响，以便于在提交前就确认最终沉淀结果。

#### 验收标准

1. GIVEN 子面板已加载当前迭代领域变更集和现有领域基线，WHEN 用户新增、修改、废弃或移动能力，THEN 系统必须实时生成对应的基线投影结果。
2. GIVEN 用户查看基线投影，WHEN 展示能力、契约和不变量内容，THEN 展示结果必须来自结构化投影计算，不得依赖跳转到主面板后再执行二次聚合。
3. GIVEN 相同的领域变更集、基线版本和注册表输入，WHEN 系统重复执行投影，THEN 投影结果必须保持确定性一致。
4. GIVEN 投影计算失败，WHEN 子面板刷新预览，THEN 系统必须阻断提交并显示失败原因。

### 需求-3：领域提交必须原子化落盘

**用户故事：** 作为主干维护者，我希望子面板提交时同时完成迭代增量与领域基线更新，且失败时不留下半成品，以便于沉淀结果始终一致可追溯。

#### 验收标准

1. GIVEN 用户在子面板触发提交，WHEN 提交成功，THEN 系统必须同时写入当前迭代的领域增量产物与更新后的领域基线产物。
2. GIVEN 提交过程中任一目标文件写入失败，WHEN 原子提交结束，THEN 系统必须保证本次提交不会留下部分成功、部分失败的中间状态。
3. GIVEN 本次提交没有实际领域变更，WHEN 用户执行提交，THEN 系统必须返回“无变更”结果，不得重复写入等价产物。
4. GIVEN 提交完成，WHEN 系统回显结果，THEN 必须明确告知处理的领域数量、能力数量以及是否存在被阻断项。

### 需求-4：冲突必须在子面板内提前检测并分类

**用户故事：** 作为领域治理者，我希望在提交前就知道本次改动会触发哪类冲突，以便于尽早处理，而不是等到主面板聚合阶段才暴露问题。

#### 验收标准

1. GIVEN 当前迭代领域变更集与最新领域基线一起参与校验，WHEN 系统执行预检查，THEN 必须检测至少以下冲突类型：命名冲突、基线版本冲突、能力主键冲突。
2. GIVEN 原始领域名无法唯一映射到注册表 canonical domain，WHEN 系统执行归类，THEN 必须标记为命名冲突并阻止直接提交到正式领域基线。
3. GIVEN 用户开始编辑后基线版本已被其他提交更新，WHEN 系统执行提交前校验，THEN 必须识别为基线版本冲突并要求重新投影。
4. GIVEN 同一 `Req-*` 在并发改动中出现互相矛盾的标题、状态或领域归属，WHEN 系统校验能力主键，THEN 必须识别为能力主键冲突并阻断自动提交。

### 需求-5：冲突裁决必须内嵌在子面板内完成

**用户故事：** 作为领域维护者，我希望命名冲突和并发冲突都能在当前子面板中处理，以便于不再依赖额外治理面板。

#### 验收标准

1. GIVEN 子面板检测到命名冲突，WHEN 用户处理该冲突，THEN 系统必须至少支持合并到已有 canonical domain、登记为已有领域别名、创建受控新领域三种裁决结果。
2. GIVEN 子面板检测到基线版本冲突，WHEN 用户选择继续处理，THEN 系统必须先拉取最新基线并重新执行投影，再决定是否允许提交。
3. GIVEN 子面板检测到能力主键冲突，WHEN 系统无法自动收敛字段差异，THEN 必须要求用户在子面板内明确选择保留值后方可提交。
4. GIVEN 冲突尚未处理完成，WHEN 用户尝试提交，THEN 系统必须阻断提交并提示仍未解决的冲突项。

### 需求-6：领域沉淀必须保持可追溯与可测试

**用户故事：** 作为审阅者，我希望每次领域沉淀都能追溯回本次迭代的具体需求和结构化变更，以便于验证结果真实且可独立测试。

#### 验收标准

1. GIVEN 子面板维护能力项，WHEN 用户保存或提交，THEN 每条能力必须绑定唯一 `Req-*` 标识，不得写入无来源能力。
2. GIVEN 领域基线完成更新，WHEN 审阅任一能力、契约或不变量，THEN 必须能追溯到本次迭代的领域变更集来源。
3. GIVEN 系统生成提交结果，WHEN 写入结构化产物，THEN 必须记录本次提交使用的基线版本、处理时间和关联迭代标识。
4. GIVEN 某条需求缺少独立可验证的验收依据，WHEN 该需求尝试进入领域沉淀，THEN 系统必须阻断并提示需求不可测试。

### 需求-7：仓库边界与外部输入必须受控

**用户故事：** 作为平台维护者，我希望子面板即使承担完整领域维护职责，也仍然严格受当前仓库边界与输入校验约束，以便于不会引入越界写入或不安全输入。

#### 验收标准

1. GIVEN 系统读取或写入领域相关产物，WHEN 解析路径，THEN 必须按当前仓库根目录解析，不得硬编码 workspace 根路径。
2. GIVEN 子面板接收领域名、Req ID、路径、状态等外部输入，WHEN 执行处理前校验，THEN 系统必须验证格式合法性并拒绝非法输入落盘。
3. GIVEN 领域维护流程需要创建或更新文件，WHEN 目标路径超出当前仓库允许范围，THEN 系统必须阻断操作并返回越界原因。
4. GIVEN 领域维护产物写入仓库，WHEN 执行安全审查，THEN 产物中不得包含硬编码密钥、凭证或未校验的外部内容。

### 需求-8：重跑与重复提交必须保持幂等

**用户故事：** 作为子面板操作者，我希望重复打开、重复预览和重复提交同一批领域变更时不会生成冲突 ID 或重复沉淀，以便于流程可重试且结果稳定。

#### 验收标准

1. GIVEN 相同的领域变更集和相同的基线版本，WHEN 用户重复打开子面板预览，THEN 系统生成的基线投影必须一致且不产生重复副作用。
2. GIVEN 同一批已成功提交的领域变更再次提交，WHEN 提交内容与已落盘结果等价，THEN 系统必须判定为幂等重放并避免重复写入。
3. GIVEN 提交后需要再次进入编辑，WHEN 用户重新打开子面板，THEN 系统必须基于最新基线状态初始化，而不是复用过期内存状态。
4. GIVEN 系统重跑当前任务，WHEN 重新生成需求或领域产物，THEN 不得产生冲突 ID、重复初始化记录或相互矛盾的结构。
